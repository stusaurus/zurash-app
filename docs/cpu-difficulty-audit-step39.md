# ズラッシュ！ 第2章 STEP39｜CPU難易度実測と初心者CPUの長期化対策

## 方針

UIの全面再設計はゲームシステム完成後にまとめて行う。今回は独立CPU対戦の強さの差、決着性、先攻後攻差の切り分けだけを扱う。ボード版のルール研究や第1・2章の進行データは変更しない。

## 比較条件

- 実際の `src/engine.js` の合法手・得点・決着判定、および `src/ai.js` の既存評価関数・探索
- 3つの既存の回転対称7×7盤面（`LAYOUTS[0]`・`[1]`・`[2]`）を使用
- 難易度別対局: 3組のCPU × 3盤面 × 2固定乱数 × 先後入替2 = **36局**。1局80手で区切る
- 同難易度の追加対局: 各難易度 × 3盤面 × 4固定乱数 = 各12局
- 手数上限・合法手なしは**未決着**として集計し、引き分けや架空の勝者を与えない
- 再現方法: `node scripts/boss-cpu-benchmark.js --full`。JSON・Markdownの個別記録はGitHub Actionsの `chapter-two-cpu-audit` artifactから取得可能（CI完了後）

れんしゅうCPUは、合法手から無作為に選び続ける方式を廃止。現在は **現在の局面から評価の高い合法手12候補まで** に絞り、重み付きランダムで少し不完全な手を選ぶ。今すぐ勝てる手だけは見逃さない。盤面・ルール・報酬は変更しない。改善後のれんしゅう同士12局は先攻5勝・後攻7勝で未決着なし。

なお、探索CPU同士の3/12未決着は**依然として未解決**。次の開発では循環・停滞原因を調べる必要がある。

## 解釈上の留意点

- すべて同一リポジトリのJSロジックを隔離V8環境で実行した測定。フル計測をGitHub Actions上でも自動再実行する。iPhone実機・人間の遊びやすさの確認ではない。
- **CPU同士の勝率だけでは人間にとっての難易度を証明できない。** 「やさしい・普通・難しい」の表示が妥当かは実際の試遊で判断する。
- 最短手数、ランク、星・結晶・家のセーブには変更なし。
- 80手は監査用の打ち切り。ユーザー対CPUの対戦に80手制限や強制決着は設けない。
- 結果は固定乱数の少数例。探索CPUの追加検証と、同一難易度・複数盤面での長期化率の調査が必要。
