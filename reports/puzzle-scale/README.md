# ズラッシュ！ 10,000ステージ対応可能性の検証

実測日：2026年10月31日。対象：`stusaurus/zurash-app`、基準コミット`040bb3fbeb95684c7d7c9edba45e8b8845a85a8d`。

## 判断

**保存・分割読込・進行管理を10,000面に拡張する技術的な見通しはある。現行の自動生成器だけで、十分に多様で面白い10,000面を揃えられるところまでは実証できていない。**

10,000候補のうち5,202面の最短解と再生成功を確認した。別の乱数系列では、選別を通した500面も再生確認できた。したがって「解ける問題を継続的に作って検証する」工程は動く。一方で、探索未判定、短い問題、同じ攻略手順への集中が残る。大量データを作成しただけの成功判定はしない。

正式採用は0面。人間による面白さ・難度調整の確認も0面。既存の対戦画面・CPU・2人戦ルールは変更せず、mainへマージしない。元の`zurash-game`には書き込まない。

## 条件

- Node v24.22.1、Linux x64、AMD EPYC 9V74、見えている論理CPU数9。探索は1プロセス・逐次実行。
- `random-v1`、seed 731031。正方形、横長、縦長、L、T、中央に穴、端の切欠きの7形状。通常は4〜9マス角の範囲で幅・高さを変更。
- 可動壁1〜3個、星1〜3個、固定障害物0〜2個。小盤面では必要な空きマスを優先して障害物数を減らす。
- 基本ルール50%、アイス・グローブ・ワープ・3種混合をそれぞれ12.5%の候補に付与。付与しただけでは使用必須とはしない。
- 1面につき最大1,500保存状態、時間上限1,000msの幅優先探索。全合法手を列挙し、局面重複だけを除く。
- 50→500→10,000は同じ候補列の入れ子。別々の独立標本ではない。
- アイテム効果は[検証仕様](../../docs/puzzle-scaling-contract.md)のsolo-v1。任意マスへの氷設置や自動転送は対象外。

## 生成・攻略検証

|候補数|配置検査済み|解あり＋最短解再生成功|全探索で解なし|探索上限で未判定|配置生成＋指紋作成|探索合計|
|---:|---:|---:|---:|---:|---:|---:|
|50|50|28|1|21|8.4ms|349ms|
|500|500|270|5|225|42.3ms|3.10秒|
|10,000|10,000|5,202|89|4,709|627ms|57.79秒|

10,000面すべてに探索を試行したが、クリア可能と確認できたのは5,202面。4,709面は「解けない」ではなく「未判定」。候補のまま保管し、正式カタログには入れない。まったく探索を試していない盤面は、この10,000候補内にはない。

探索時間は1面あたり中央値5.45ms、95パーセンタイル14.78ms、最大37.55ms。配置生成、再生、圧縮、補助測定、大盤面試験を含む実験全体は63.58秒。GPU・分散処理・サーバー課金は使っていない。

量産中に小さいT字盤面で配置用のマスが足りなくなる不具合を発見し、ソケットとポータルのマスを先に予約するよう修正した。最終の10,000候補で配置不整合0件を確認し、10,000件の配置生成テストも追加した。修正前の中断結果を最終集計には混ぜていない。

## 重複・難度・攻略の偏り

- IDを除く配置の完全重複：0。回転・反転しただけの重複：0。
- 解けた5,202面の最短手数：1手451面、2手1,141面、3手1,379面、4手931面、5手525面、6手323面。残り452面は7〜17手。
- 1〜2手で終わる問題は1,592/5,202＝30.60%。導入用には使えても、長期コンテンツの大部分としては弱い。
- 回転・反転を揃えた「準備の種類＋滑走方向」の攻略手順は1,531種類。上位10種類に32.24%が集中。
- 滑走距離と星を取るタイミングまで含めた手順は3,803種類。

配置が別でも似た遊びになり得ることを確認した。上記は保存された最短解1本の類似度であり、全解集合や人間の体験が同じかの判定ではない。逆に、細かい移動距離が違うだけで実質的に同じ問題を過小評価する余地もある。

最短手数は人間の難度ではない。見落としやすさ、誘導、戻り操作、誤答からの復帰、操作時間、解けたときの納得感は未測定。

## アイテム拡張

3種の使用・消費・状態保存・探索・再生を実装した。解けた面の保存手順には、氷設置231回、グローブ396回、ワープ120回が含まれる。

各アイテムが手順に現れる面を先頭から40面ずつ選び、そのアイテムの残数を0にして再探索した。

|削除したアイテム|ないと解けないと全探索で確認|最短手数が増加|同じ最短手数|探索上限で不明|
|---|---:|---:|---:|---:|
|アイスブロック|2|22|12|4|
|パワーグローブ|0|20|18|2|
|ワープクリスタル|3|21|13|3|

単にアイテムを配置するだけでは意味のある問題にはならない。最短解にアイテムが出てきても、使わない同手数解がある。グローブを必須とする盤面は、この標本では証明できていない。標本は使用例から選んでおり、全候補の必要性率を推定するための無作為抽出ではない。

## 独立した生成・選別の追試

seed 941101の別系列で、次の自動選別を実施した。

1. 最短3手以上。
2. 基準実験の候補および選別済み面と、回転・反転を含めた配置が重複しない。
3. 同じ「準備の種類＋滑走方向」の攻略手順は最大3面まで。
4. アイテム付き問題は使用手順を持ち、さらに全アイテムをなくした場合より短い最短解、またはアイテムなしでは不可能と確認できること。
5. 抽出した手順を再生してクリアすること。

2,436候補から500面を抽出。採用率20.53%、12.81秒。全500面を再生成功。最短3〜12手、攻略手順387種類、同一手順は最大3面。内訳は基本424、氷14、グローブ26、ワープ13、混合23面。手順中に氷を使う面28、グローブ40、ワープ15面。

これは研究上の抽出であり、製品への採用ではない。500面の手順を含む証拠を`curated-pool.json.gz`に保存した。基準実験と合わせ、保存したクリア手順で確認できる異なる盤面は5,702面。

20.53%の率が一定なら1万面に約4.9万候補が必要という試算になるが、その率が続くとは実証していない。手順の上限に達すると採用率が下がる可能性があり、今回の500面から10,000面への外挿だけで成功判定はできない。

|単一JSONをgzip圧縮|300,864 bytes|
|100面単位のチャンク|100ファイル、中央値46,270 bytes、最大47,383 bytes|
|チャンク単位のgzip|中央値3,716 bytes、最大3,866 bytes|

|1,000回ランダム読込|中央値0.737ms、95%点1.017ms、合計777.5ms|
|合成10,000クリア履歴のJSON|520,037 bytes|

読込はNodeのローカルファイル、Web Crypto、3チャンクのLRU。ランダム1,000回ではキャッシュ外アクセスが多く、1,001読込・46.32MBの累計読込となった。順番に進む通常プレイとは条件が異なる。先読みは次の1チャンク程度に絞るべきであり、全ステージの毎回取得は不要。

保存先は測定時にメモリのStorage代替を用いた。**ブラウザのlocalStorage書込時間、実機iPhone、モバイル回線、実際のゲーム画面での負荷を測った数値ではない。** ブラウザ用測定器とCIを追加したが、ローカル環境にはブラウザ実行ファイルがなく、ネットワーク制限によりインストールも失敗した。失敗を`browser-performance.json`に記録している。ブラウザ測定が通るまではブラウザ性能を実証済みとしない。

10,000クリア履歴は容量を試す合成データ。10,000面が解けたことの証明に流用しない。

初回クリア→星1個→建築で支出→再クリアで星が増えない→保存・復元という整合性はコードとテストで確認した。旧ステージ版の再実行、改訂、残高不足、同じ建築の二重実行、破損データ、保存容量エラーも検査した。クラウド同期・課金・サーバー側認証は未実装。

## 具体的な限界

- 12〜16マス角、壁6個、星4個の28候補を10,000状態・2秒上限で探索したが、28面とも未判定。大きな盤面を自由に増やすだけでは現在の全幅探索は足りない。
- 本実験の最大RSSは319,472KiB（約312MiB）。10,000候補・証拠の一括保持を含む開発用プロセスの値であり、ブラウザ1ステージの必要メモリではない。
- 盤面の面積だけでなく、動かせる壁数、星数、氷の設置候補数、残数などの積で状態数が膨らむ。
- 盤面形状には通行マスクで対応できるが、16を超える一辺、時間変化、移動する敵、複数コマ、ランダム効果、追加の勝利条件は未検証。
- 人間の1問あたりのプレイ時間、継続率、課金設計とのバランス、解説UI、ヒント提供、通信障害からの復帰は未検証。
- カタログの並べ替えと恒久IDの独立、改訂時の証明再生成、完全な移行・バックアップは本格運営前に追加する。

次の探索改善は「面積拡大」より、難度帯別の状態数制限、可動壁数の制御、ゴールからの構成的生成、到達不能条件の事前検査、メモリを制限した反復深化などを比較する。今回、それらの改善効果は測っていない。

## 最初の50面への設計提案

7形状＋3アイテムで、少なくとも数千の解ける候補を出せる。ただし「何種類あれば面白い1万面に十分か」という最小数は今回の実験から決められない。種類数の水増しより、星を取る順番、壁を先に仕込む、往復して戻る、限られた使用回数を配分する、といった判断の違いを重視する。

当初50面は3アイテムを第10面までに触れられる設計を推奨する。3種は検証用効果を試遊してから確定する。街づくりは初回クリアの星1個で進め、問題の最短手数評価と街用通貨を分ける。

|面|狙い|盤面と機能の目安|
|---|---|---|
|1〜2|滑る・停止して星を取る・壁を1マスずらす|4〜5マス角、説明を短く。1〜2手問題は主にここ|
|3〜5|氷で停止位置を作る|氷を導入。使うとどう変わるか見て理解できる配置|
|6〜8|壁を遠くへ動かして経路を作る|グローブ導入、長方形を少しずつ使う|
|9〜12|離れた場所をつなぐ|ワープ導入。3種とも使える状態へ|
|13〜20|同じ道具を別の判断で使う|L・切欠き、星取得順、基礎だけの復習も混ぜる|
|21〜35|準備した壁が後で役立つ|5〜7マス中心、2機能の組合せ、短い回復面を挟む|
|36〜50|既習要素の組合せと章の達成感|少数の穴・T形、節目の問題と街の変化を結ぶ|

これは制作順の提案で、50面を制作済みという意味ではない。探索で最短手数とアイテム効果を確認し、人間の試遊で順序・見た目・誤操作・難度を調整する。50面を通した理解度と再挑戦意欲が見えてから、100〜500面の章構成を固める。将来は形状6〜8系統と3種の基本アイテムを土台に、必要が実証された追加ギミックを段階導入する。この数は設計上の開始案で、1万面の十分条件ではない。

## 再現と証拠

```sh
npm test
npm run check
npm run puzzle:verify
# 基準実験を再生成
npm run puzzle:study
# 独立系列で500面を選別
npm run puzzle:curate
# ブラウザと依存関係を用意した環境
npm ci
npx playwright install --with-deps chromium webkit
npm run puzzle:browser
```

`summary.json`、`milestone-*.json`、`manifest.json`に条件・集計・容量を保存。`chunks/`は未採用候補10,000面。`verification.jsonl.gz`は10,000件の探索結果と5,202件の手順。`item-ablation.json`、`large-board-stress.json`、`curation-summary.json`、`curation-ledger.jsonl.gz`、`curated-pool.json.gz`は追加検証の原データ。gzip内のJSON/JSONLは標準のgzipで展開できる。

配置チャンクはSHA-256を検証。検証台帳と選別プールにもハッシュを保存。`puzzle:verify`で5,202＋500手順を再生し、89件の不可能結果を再探索する。探索手数の最短性は生成時の全幅BFSの性質によるもので、再生器だけから証明しているわけではない。

ローカルでは既存を含む60テスト、構文チェック、全保存手順の再生、配置・証拠のハッシュ整合性が成功。ブラウザでの操作試験は未完了。CIには同じ検証とブラウザ測定を追加し、再生成は手動実行に限定した。
